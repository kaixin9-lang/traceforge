# TraceForge 项目启动指南

适用环境：本机 Windows PowerShell、WSL Ubuntu，以及当前已安装好的 TraceForge 项目。

项目目录：`D:\systemDir\Documents\ChatGPT\agent_program`。

本机的 Python 环境、前端依赖、模型和容器镜像已经准备好。电脑重新开机后，按照下面的启动步骤操作即可，无需重新安装。

## 1. 开机后快速启动

### 第一步：确认 Ollama 已打开

从 Windows 开始菜单打开 Ollama。如果右下角托盘已有 Ollama 图标，可直接进行下一步。启动脚本不会自动启动 Ollama。

可以在 PowerShell 中检查嵌入服务：

```powershell
Invoke-RestMethod 'http://127.0.0.1:11434/api/tags'
```

如果无法连接，先打开 Ollama。也可以在一个单独的 PowerShell 窗口运行 `ollama serve`，并保持该窗口运行；已有 Ollama 服务时无需再次运行。

### 第二步：运行启动脚本

打开 PowerShell，依次执行：

```powershell
cd D:\systemDir\Documents\ChatGPT\agent_program
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\start.ps1 -SkipBuild
```

等终端出现：

```text
TraceForge已启动：http://127.0.0.1:8000
```

`-SkipBuild` 表示使用已经构建好的前端，适合重启电脑后直接使用。上面的执行策略参数只用于本次 PowerShell 子进程。

如果需要同时启动 Java、MySQL、Nginx 等演示容器，将上面的启动命令替换为：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\start.ps1 -SkipBuild -WithDemos
```

两条启动命令选择一条运行即可。服务已经启动时，再次执行脚本会提示已有实例。

### 第三步：打开工作台

浏览器访问 [TraceForge 工作台](http://127.0.0.1:8000/)。

然后运行完整健康检查：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\health.ps1
```

检查输出中的 `app`、`ollama`、`milvus`、`deepseek`、`reranker`、`mcp.local` 和 `mcp.docs`。相应的 `ok: true` 表示该项检查通过。

“已启动”表示 Web 后端可以响应请求；完整健康检查用于进一步确认模型、知识库和工具连接。首次检索可能需要加载本地重排模型。DeepSeek 调用需要联网。

## 2. 两种启动模式怎么选

### 日常使用：部署模式，访问 8000

使用第 1 节的 `start.ps1` 启动。

这个模式只有一个 Web 后端进程监听 `8000`，FastAPI 同时提供：

- `/`：前端入口页面。
- `/assets/...`：构建好的 JavaScript、CSS 等前端文件。
- `/api/v1/...`：后端业务接口。

浏览器下载页面文件后，React 在浏览器中运行，再向同一个地址请求 API。因此，前端页面和后端接口可以共用 `8000`。

在该模式下修改前端源码，需要重新构建，操作见第 5 节。

### 修改前端：开发模式，前端 5173，后端 8000

后端仍使用 `8000`，另外启动 Vite 前端开发服务器监听 `5173`。Vite 会把前端的 `/api` 请求代理到 `http://127.0.0.1:8000`。

**PowerShell 窗口 A：启动后端和依赖。**

如果后端已经运行，可直接进行窗口 B 的操作。后端未运行时执行：

```powershell
cd D:\systemDir\Documents\ChatGPT\agent_program
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\start.ps1 -SkipBuild
```

**PowerShell 窗口 B：启动前端。**

```powershell
cd D:\systemDir\Documents\ChatGPT\agent_program\frontend
npm.cmd run dev -- --port 5173 --strictPort
```

浏览器访问 [前端开发页面](http://127.0.0.1:5173/)。修改前端源码后，Vite 会自动更新页面。

`--strictPort` 会在 `5173` 已占用时明确报错，避免自动切换到其他端口。目前后端允许的开发页面来源包括 `127.0.0.1:5173` 和 `localhost:5173`。

保持窗口 B 运行。关闭开发页面时，可在该窗口按 `Ctrl+C` 停止 Vite。`stop.ps1` 不负责停止这个手动启动的 Vite 进程。

## 3. 启动脚本具体做了什么

[启动脚本 start.ps1](D:/systemDir/Documents/ChatGPT/agent_program/scripts/start.ps1) 的执行顺序为：

1. 切换到项目根目录，检查独立 Python 环境是否存在。
2. 根据参数决定是否执行前端构建。
3. 检查已有 TraceForge 后端或资料 MCP 进程，避免重复启动。
4. 复用或启动后台 WSL 保活进程，并启动 Docker 服务。
5. 先启动独立 etcd，健康检查通过后启动 Milvus，并等待真实数据库调用就绪；再从 Windows 检查 Milvus RPC。使用 `-WithDemos` 时同时启动演示容器。即使后端已运行，也会执行这一步来恢复向量库。
6. 使用 `.venv\Scripts\python.exe` 启动资料 MCP 服务。
7. 使用同一个 Python 环境启动 Uvicorn / FastAPI 后端。
8. 记录进程 ID，并检查 `/api/v1/session` 是否可以访问。

后端的核心命令是：

```powershell
.\.venv\Scripts\python.exe -m uvicorn traceforge.api:app --host 127.0.0.1 --port 8000
```

其中 `traceforge.api:app` 指向 [traceforge/api.py](D:/systemDir/Documents/ChatGPT/agent_program/traceforge/api.py) 中的 FastAPI `app` 对象。应用启动时读取后端 `.env`，初始化 LangGraph 和 SQLite checkpoint，并连接两种 MCP 服务。

脚本用隐藏的后台进程运行后端和资料 MCP，所以正常启动后不会一直显示日志窗口。Ollama由用户单独启动；本地 stdio MCP 由后端在连接工具时启动。

## 4. 手动启动后端，查看实时日志

这个方式适合调试 Python 后端。先退出已有后台实例，避免两个 Uvicorn 进程竞争 `8000`。

### 4.1 准备依赖并退出后台 Web 服务

确认 Ollama 已运行。如果本次开机尚未启动过项目，先运行启动脚本，让 WSL、Docker 和 Milvus 就绪，再停止后台 Web 服务：

```powershell
cd D:\systemDir\Documents\ChatGPT\agent_program
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\start.ps1 -SkipBuild
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\stop.ps1 -KeepMilvus
```

如果项目已经运行，只需执行最后一条停止命令。

`-KeepMilvus` 保留 Milvus、演示容器和已登记的 WSL 保活进程；该停止脚本仍会停止 Web 后端、资料 MCP，以及应用管理的宿主机演示服务。

### 4.2 窗口 A：启动资料 MCP

```powershell
cd D:\systemDir\Documents\ChatGPT\agent_program
$env:PYTHONIOENCODING='utf-8'
.\.venv\Scripts\python.exe -m traceforge.mcp_servers docs
```

这个服务使用 `8001` 端口。保持该窗口运行。

### 4.3 窗口 B：启动 FastAPI 后端

```powershell
cd D:\systemDir\Documents\ChatGPT\agent_program
$env:PYTHONIOENCODING='utf-8'
.\.venv\Scripts\python.exe -m uvicorn traceforge.api:app --host 127.0.0.1 --port 8000
```

看到 `Uvicorn running on http://127.0.0.1:8000` 后，后端已开始监听。请求和异常日志会直接出现在该窗口。

调试结束后按 `Ctrl+C` 停止。修改 Python 代码后，重新运行命令使修改生效。重启后端后，刷新浏览器获取新的会话。

如需前端热更新，再打开窗口 C，执行第 2 节的 Vite 命令，访问 `5173`。

## 5. 修改代码或配置后的重启

### 修改前端源码，继续使用部署模式

停止已有实例，再启动时省略 `-SkipBuild`：

```powershell
cd D:\systemDir\Documents\ChatGPT\agent_program
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\stop.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\start.ps1
```

脚本会先运行前端构建，再启动服务。需要演示容器时，在最后一条命令后加 `-WithDemos`。

### 修改后端源码或 .env

只需重启后端相关服务，可以保留 Milvus：

```powershell
cd D:\systemDir\Documents\ChatGPT\agent_program
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\stop.ps1 -KeepMilvus
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\start.ps1 -SkipBuild
```

随后刷新页面，再运行健康检查。密钥保存在后端 `.env` 中，启动时自动读取，无需放入前端。

## 6. 停止项目

正常停止：

```powershell
cd D:\systemDir\Documents\ChatGPT\agent_program
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\stop.ps1
```

停止脚本会停止 TraceForge Web 后端、资料 MCP、应用管理的宿主机演示服务、Milvus和演示容器，以及已登记的 WSL 保活进程。

它会保留知识库、SQLite 记录、Milvus 数据卷、修复备份和模型文件。再次启动后可查看已有历史与审核记录。停止或重启期间的诊断可能变为中断或取消状态；显示“已中断”的任务可从工作台恢复，继续操作前先确认任务状态。

手动运行的 Vite 和 Ollama 命令窗口，需要分别用 `Ctrl+C` 停止。

## 7. 常见报错

### 7.1 后端启动报 WinError 10048

含义：`127.0.0.1:8000` 已有进程监听，又启动一个 Uvicorn 实例就会冲突。

查询监听进程：

```powershell
Get-NetTCPConnection -State Listen -LocalPort 8000 | Select-Object LocalAddress,LocalPort,OwningProcess
```

如果已有 TraceForge 正常运行，直接访问工作台；开发前端时额外启动 Vite 即可。如果需要手动调试后端，按第 4 节先停止已有实例。

### 7.2 脚本提示“服务已经运行”，但工作台打不开

启动脚本会分别检查后端和资料 MCP 两种进程，仅启动缺失的服务。如果现有后端进程没有正常响应，脚本会等待接口并报告超时。

先运行健康检查。确认服务异常后，按第 5 节停止并重新启动项目。

### 7.3 提交诊断显示 Failed to fetch / 无法连接本机后端

含义：浏览器没有取得 API 响应。页面可能是之前已加载的内容，显示页面本身不能证明后端还在运行。

按顺序处理：

1. 确认使用 `8000` 部署页面，或使用已运行 Vite 的 `5173` 开发页面。
2. 在 PowerShell 运行启动脚本，等出现“TraceForge已启动”。
3. 刷新浏览器，重新获取后端会话。
4. 运行健康检查，查看具体失败组件。
5. 如果仍失败，查看后端日志和端口监听状态。

### 7.4 页面提示“会话已过期，请刷新工作台”

后端每次启动会生成新的会话令牌。旧页面仍持有之前的令牌时会出现该提示，刷新页面后重试即可。

### 7.5 Ollama 或嵌入服务不可用

确认 Ollama 已启动，再检查模型清单：

```powershell
ollama list
```

本项目使用 `qwen3-embedding:0.6b`。确认模型存在，并检查 `11434` 接口是否响应。本机已有模型，重新开机无需重新下载。

### 7.6 Milvus / Docker 启动失败

在 PowerShell 检查 WSL 和容器状态：

```powershell
wsl --list --verbose
wsl -d Ubuntu -u root -- systemctl is-active docker
wsl -d Ubuntu -u root -- docker ps --filter name=traceforge
```

确认 Ubuntu 可以启动、Docker 为 active、`traceforge-etcd` 和 `traceforge-milvus` 均为 healthy。随后重新运行启动脚本与健康检查。

如果后端正常但向量库显示 `All connection attempts failed`，先检查容器是否正在反复重启：

```powershell
wsl -d Ubuntu -u root -- docker logs --tail 200 traceforge-milvus
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\start.ps1 -SkipBuild
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\health.ps1
```

本机曾在 Milvus 3.0.2 的内置 etcd 恢复时触发 `panic: etcdserver: leader changed`。现配置改用同版本的独立 etcd 3.5.33，复用原卷中的 `/var/lib/milvus/etcd` 元数据，并用 `service_healthy` 保证启动顺序。启动脚本会等待两个容器健康，失败时不会继续报告启动成功。无需删除数据卷或重新导入资料。

随后出现的 `failed to create etcd client: context deadline exceeded` 与 WSL 中 Docker 网桥的转发规则不匹配有关：etcd 在自身容器里健康，其他容器却无法连接它。现配置通过 `network_mode: service:etcd` 让两个服务共享网络空间，Milvus 经 `127.0.0.1:2379` 访问 etcd；客户端端口 `19530` 和管理端口 `9091` 由 etcd 容器映射到 Windows 本地地址。

Milvus 的 `/healthz` 曾在初始化未完成时返回 OK，因此现容器健康检查使用实际集合列表接口，后端健康检查使用配置中的 Milvus RPC 地址。可以单独验证真实连接：

```powershell
.\.venv\Scripts\python.exe .\scripts\check-milvus.py
```

### 7.7 DeepSeek 检查失败或诊断出现模型调用错误

确认当前网络可以访问 DeepSeek API，并检查后端 `.env` 的 `DEEPSEEK_API_KEY` 和 `DEEPSEEK_MODEL`。本项目配置的默认模型是 `deepseek-flash`。

本机直连DeepSeek曾在连接建立阶段间歇性超时，目前通过已有代理`http://127.0.0.1:7897`访问，运行项目时保持代理开启。该地址在`.env`的`DEEPSEEK_PROXY_URL`中配置，仅供DeepSeek健康检查、模型调用和Ragas评估使用。其他环境可以将此项留空以直连。

健康检查对网络超时和临时服务端错误最多尝试两次。持续失败时会显示具体错误类型与中文说明；401表示鉴权失败、402表示账户余额不足、429表示请求限流，不再显示空白错误。模型不在可用列表时也会明确提示。

修改 `.env` 后重启后端。如果只是临时网络超时，可以重新运行健康检查，判断是否恢复。`app.ok` 为 true 只说明本机后端可响应，DeepSeek 的结果需要单独查看。

### 7.8 前端改了代码，页面还是旧版本

- 在 `8000` 查看构建后的页面：按第 5 节重新构建并启动，再刷新浏览器。
- 在 `5173` 查看开发页面：确认 Vite 窗口仍运行，并且浏览器访问的是 `5173`。

## 8. 日志、地址与相关文件

以下日志路径相对于项目根目录：

- `data\backend.out.log`：脚本启动后端时的 HTTP 请求记录。
- `data\backend.err.log`：后端启动信息、警告和异常。
- `data\mcp.out.log`、`data\mcp.err.log`：资料 MCP 日志。

- `data\processes.json`：启动脚本记录的进程 ID，重启后以实际进程状态为准。

```powershell

Get-Content .\data\backend.out.log -Tail 80
```
