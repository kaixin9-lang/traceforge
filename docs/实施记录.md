# 实施记录

项目按用户确认的计划实施，课程前五章及19篇页面已读取。课程正文没有进入初始知识库。

实际环境问题及处理：

- Windows进程代理导致部分依赖TLS失败，使用可验证的直连路径与国内包源；CUDA wheel使用官方PyTorch源。
- WSL中的Docker Hub DNS/连接失败，Docker daemon使用本机既有代理；容器命令的默认网络仍关闭。
- Milvus嵌入etcd需要DEPLOY_MODE=STANDALONE，已修正并实测建集合、入库与检索。
- WSL空闲退出导致向量服务断连，部署启动增加后台保活进程。
- FastMCP4/MCP2与当前LangChain适配器不兼容，锁定FastMCP3与MCP1组合。
- Ragas0.4.3依赖旧community模块，锁定community0.4.1，未修改第三方源码。
- Milvus3主键和分数字段为pk/distance，已用真实结果验证映射并加回归测试。
- WSL参数使用--exec，避免宿主Linux shell对容器命令提前解释；实测字面命令替换没有展开。
- 审核状态写入和checkpoint持久化存在时间边界，恢复前等待原任务进入中断完成状态。
- 浏览器编辑提案后需要重置编辑状态，真实审核E2E验证后修正。
- Windows PowerShell5读取无BOM中文脚本有编码问题，交付脚本采用UTF-8 BOM。
- Ragas评审有网络中断与输出截断，使用原始样本有界重试，并提高评审输出上限。

完整模型链路、四类故障闭环、宿主机服务、截图、MCP资源/提示词、容器边界、SSE与取消、检索与六项评估均有实际测试输出。最终数量和得分见测试报告。

## 2026-10-09 向量库连接恢复

后端健康接口中仅Milvus失败，错误为`All connection attempts failed`。WSL和Docker正常，Milvus3.0.2容器以退出码134反复重启，`OOMKilled=false`。日志显示内置etcd恢复并选举主节点时，Milvus已开始注册服务，收到`etcdserver: leader changed`后在`Session.Init`触发panic。

停止崩溃容器后，将原配置和完整数据卷备份至`data/backups/milvus-startup-20261009/`。改用与内置版本一致的独立etcd3.5.33，复用原命名卷中的元数据目录，Milvus版本和集合保持原样。Compose增加etcd健康依赖；启动脚本增加`--wait`，并允许在已有Web进程运行时修复向量库依赖，复用已登记的WSL保活进程。

恢复后原集合`traceforge_chunks_v1`统计为416条记录。Windows端SDK连接成功，后端健康接口返回`milvus.ok=true`；真实混合检索的稠密和BM25路线各召回20条，最终返回5条证据且无告警。

完整停止etcd与Milvus后再次运行启动脚本，两个容器均恢复healthy且自动重启次数为0；已有Web进程和WSL保活进程复用成功。

参考：[Milvus etcd配置](https://milvus.io/docs/configure_etcd.md)、[Docker Compose启动顺序](https://docs.docker.com/compose/how-tos/startup-order/)。

## 2026-10-09 再次连接故障与健康检查修正

当天再次排查时，etcd持续健康，Milvus累计自动重启174次。Docker事件显示多次运行约10秒即以134退出，日志为`panic: failed to create etcd client: context deadline exceeded`。Docker实际使用`br-6a139b816374`网桥，FORWARD/DOCKER-FORWARD/DOCKER-BRIDGE规则却只覆盖另一组网桥。DNS能够解析etcd到`172.18.0.2`，但Milvus容器内按名称和IP连接均超时；etcd自身网络空间的真实endpoint health检查成功。已确认网桥转发规则不匹配，覆盖规则的具体进程尚未确定。

旧健康检查只访问9091端口的`/healthz`，该接口在Milvus尚未连接etcd时也短暂返回OK，因而页面和Compose可能误报健康。前一次修复的启动与检索验证证明当时可用，但不足以证明后续环境变化下持续稳定。

将新一轮配置和完整数据卷备份到`data/backups/milvus-network-20261009/`。保留独立etcd的启动顺序，使用`network_mode: service:etcd`共享网络空间，Milvus经回环地址连接etcd，绕开网桥转发；映射端口仍限定为本机127.0.0.1。未改动宿主机防火墙或其他发行版设置。容器健康检查改用实际集合列表REST调用，后端健康检查改用配置中的RPC连接；启动脚本增加Windows端RPC验证，并分别补齐缺失的后端/MCP进程。

新增健康检查回归测试，覆盖HTTP成功但RPC失败的误报，以及配置端点的使用与连接释放。与原核心单元测试合计12项通过。

实测停止向量服务后，后端健康接口正确返回`milvus.ok=false`；完整重启后恢复成功，已有后端、资料MCP与WSL保活进程未重复创建。连续182秒完成19次真实RPC和数据检查，原集合保持416条记录，两个容器均healthy、自动重启次数为0。观察前后使用已有后端做混合检索，稠密与BM25各召回20条，最终5条证据、无告警。验证输出保存在`data/milvus-network-stability.json`。

参考：[Docker共享服务网络空间](https://docs.docker.com/reference/compose-file/services/#network_mode)、[Docker iptables规则](https://docs.docker.com/engine/network/firewall-iptables/)。

## 2026-10-09 DeepSeek间歇连接失败

后端健康接口返回`deepseek.ok=false`且detail为空，其他组件正常。复现原8秒检查时得到`ConnectTimeout('')`；`str(error)`为空导致界面丢失错误原因。DNS的两个IPv4节点均能完成TLS握手，鉴权后的模型列表可返回`deepseek-flash`，真实SDK生成亦成功，确认密钥和当前模型可用。

进一步跟踪连接事件时，直连出现`connection.connect_tcp.failed`，在TLS握手和API鉴权之前已超时；一次重试后仍能复现失败。相同时段对本机已有`http://127.0.0.1:7897`代理的8次并行对照请求全部成功。已确认直连连接建立阶段不稳定，未将具体网络设备或运营商归为已确认原因。

新增可选`DEEPSEEK_PROXY_URL`配置，并在本机指定已有代理。健康检查、ChatDeepSeek的同步/异步客户端及Ragas评估共享同一连接设置。对网络错误和5xx健康请求增加一次有界重试，鉴权与余额等错误不重试；错误详情补充类型及中文提示，模型缺失也能明确报告。密钥值保持原样且未进入日志或验证结果。

回归测试覆盖一次空白连接超时后恢复、持续空白连接/读取超时、401/402/403不重复请求以及模型缺失；与已有核心与向量健康测试合计19项通过。

重启后端后，显式代理下的真实SDK生成成功。后台模型驱动的查询改写生成4条实际查询，BM25各召回20条，最终5条证据且无告警。随后55秒内的12次强制健康检查全部成功，向量库也保持正常；结果保存在`data/deepseek-recovery.json`。当前连接方案依赖本机7897代理运行，其他环境可将代理配置留空以直连。

参考：[DeepSeek错误码](https://api-docs.deepseek.com/quick_start/error_codes/)、[HTTPX代理配置](https://www.python-httpx.org/advanced/proxies/)。
